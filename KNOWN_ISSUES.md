# Known issues — test build

This reconstructed work is a prototype, not v1.0.0. Do not use real funds.

- Seed restoration scans both chains with a 20-address gap on first synchronization; balances beyond that gap are not discovered. A recovered wallet can show an incomplete balance. Keep the original seed and use a verified wallet to recover funds.
- For valid BIP39 phrases the current GUI source offers explicit standard NFKD and historical MC raw UTF-8 passphrase derivations. These can produce different wallets and addresses for Unicode input; whitespace is significant, and an incorrect passphrase or mode cannot be detected automatically. Existing create and agent behavior remains historical. Existing wallets are not reinterpreted on open; tests with selected old binaries and synthetic data do not establish compatibility with every legacy wallet or unsupported seed format.
- The restore form blocks navigation and inputs during its request and avoids publishing a delayed GUI session after unmount. The backend request cannot be cancelled and may already have created a wallet; leaving the view does not automatically remove or close it. Login accessibility labels were made distinct, but this does not prove all accessibility states are reliable.
- Mainnet only: testnet and STN are blocked until address formats, connection state and wallet databases are separated by network.
- Legacy schema 33 stores the TOTP secret in plaintext and uses password-derived AES-CBC without authenticated encryption or a memory-hard password KDF. The current schema 34 implementation uses an authenticated encrypted bundle; existing schema 33 wallets remain unchanged unless the explicit supported migration is requested. Automatic locking and complete memory zeroization are not implemented.
- Previously generated recovery codes contain eight random base-32 characters (40 bits per code) and remain valid until explicitly replaced or consumed. Newly generated codes contain 32 random base-32 characters (160 bits); their verifiers use unsalted SHA-256, a fast hash. In schema 33 the verifier is stored in the wallet database, so access to that verifier permits offline guessing. In schema 34 the verifier is inside the AEAD bundle, so this offline guessing requires access to the decrypted bundle or verifier; AEAD does not increase the code entropy. Multiple valid codes increase the chance of a guess. The low entropy of still-valid 40-bit codes remains an open security weakness; no practical exploitation is claimed. The new 160-bit random codes do not require a memory-hard verifier to compensate for low entropy. See `security/totp.rs` and `services/wallet_security.rs`.
- If a recovery-code generation response is lost after commit, previous codes may already be invalid and the new plaintext codes cannot be recovered from the wallet. Do not retry automatically; reopen and check the same wallet before deliberately generating another set. Legacy TOTP disable now changes the TOTP secret and recovery list in one transaction; commit-boundary tests do not prove the outcome of an interruption inside SQLite's commit operation.
- Imported private keys and the old legacy seed migration/sweep are disabled: synchronization and spending of those keys have not been implemented safely. Existing imported keys must be recovered using a compatible wallet.
- UTXOs are checked against fetched raw transactions, but complete chain inclusion, proof of work, full consensus, server omissions, height claims and network compatibility remain unverified. Coinbase outputs are excluded from spending until maturity can be checked reliably.
- Sync commits the collected account snapshot atomically, but server responses are gathered over time and do not constitute an atomic chain snapshot. History amounts remain unknown when a required previous transaction is unavailable; generic server errors abort sync. A server may omit data or make incorrect height claims, so balances and history remain unverified against consensus.
- A reproduced GUI defect that could show a failed history request as an empty history, or omit a failed balance request, has been fixed in the current GUI source. Loading, errors and known-empty results are distinguished; malformed history and incomplete, duplicated or unsafe-integer balance data are rejected. Focused GUI tests passed 33/33 and the TypeScript check and build passed. The complete GUI suite passed 76/76 tests in 13 files and the new release was built; the preceding Rust results concern the unchanged backend and were not rerun for this GUI-only change.
- Sync is limited to 4 MiB per raw transaction, 4,096 unique transaction fetches, 64 MiB total fetched raw transaction data, 100,000 history entries and 50 MiB per ElectrumX frame (including the newline). Exceeding a limit aborts synchronization with an error rather than saving partial amounts; large BSV transactions or histories may therefore be unsupported.
- Explicit schema 33→34 migration in the current release rejects unsupported inventories rather than migrating them. SQLite free pages, WAL, filesystems and old backups can retain legacy secrets and fast password verifiers; migration does not securely erase them. Backup path protections do not defend against processes with the same UID or parent-directory renames. Commit interruption can have an unknown outcome and requires reopening. The migration has been tested with synthetic wallets; unsupported and real-world legacy inventories remain incompletely verified.
- Multisig signing is explicitly disabled for the durable spend ledger. Console, hardware-wallet support and several ecosystem integrations require implementation or verification.
- The current source hardens password changes and Linux backups, but concurrency and crash recovery need further review. Backup requires Linux `openat2` and accessible `/proc/self/fd`, accepts only destinations inside the data directory and does not overwrite. It does not protect against processes with the same UID or a renamed parent directory. Staging or initialization failures can leave artifacts; a directory fsync failure after publication can report an error even though the backup exists. Check the destination before retrying. Windows and macOS builds have not been verified.
- The newer GUI source wires backup into the menu with password and applicable TOTP authentication. A random instance token prevents a queued GUI backup from silently targeting a different opened wallet; the token is not authentication. A failed or lost response can leave publication uncertain: check the destination before any deliberate retry. Amount validation and stale fee, receive/QR and history-detail response guards were also strengthened; these checks do not prove a complete payment flow.
- The `7c68b352…` offline release passed isolated agent migration/restore, payment and maintenance smokes; the agent backup path does not exercise the GUI instance token. A private GUI backup passed through the token-bound Tauri call, followed by process exit and separate agent open/unlock and integrity check of the backup. A second private check found the setup QR heading, verification control and input. A subsequent private GUI run confirmed TOTP activation and an accessible recovery control, then failed at recovery-code generation; whether the selector or backend caused the failure is under investigation. The setup secret was read only in memory. Code delivery, recovery, replay and backup with active 2FA remain unverified; the stale-token race was tested separately in the backend. No live test has been performed on this artifact.
- The newer `5b10e6e6…` release adds explicit visible labels and groups for recovery and disable without changing the handler policy. GUI tests passed 106/106 and the build passed; isolated offline agent migration, payment and maintenance smokes also passed. A private GUI run created a wallet, set up 2FA, used the labelled recovery card, generated ten codes read only in memory and showed completion after an explicit recovery action; subsequent unlock failed and the run exited with an error. It does not independently verify backend policy, code consumption, replay rejection, successful unlock or complete recovery. This artifact has not had a live test. Earlier Rust results belong to the previous source freeze.
- Release `5db137b7…` passed an offline build, dependency check and isolated agent migration/restore, payment and maintenance smokes. The source checkpoint passed 635 Rust tests across separate runs and 114 GUI tests plus build. A private GUI run restored a public Unicode fixture with spaces in both modes, reached the main view and closed each wallet; after GUI exit, an agent reopened and unlocked both as schema 34 and their xpubs matched independent vectors. This does not establish compatibility with arbitrary wallets or complete history. Another private GUI run covered 2FA setup, ten codes read only in memory, the recovery message, password unlock, the main view and setup control. Those UI observations alone do not independently prove backend code destruction or replay rejection. No live test was performed; updating the live script is not a live test.
- The Linux payment tests use synthetic fixtures and mock broadcast. Process-kill tests cover PREPARED and BROADCAST_UNKNOWN; a synthetic snapshot test covers confirmed change and a subsequent reorg. They do not prove a real broadcast or chain consensus. A read-only live TLS smoke on `b0291fbd…` used a public test wallet and completed sync with zero balance and 81 history entries, without payment or broadcast. It does not establish that the server's claims are true or independently validate the chain. The `3d4b4a9c…` artifact passed isolated agent migration, payment and maintenance smokes, but has not had a live test. A private, offline GUI partial flow on `3d4b4a9c…` covered synthetic wallet creation, visible history and balance text, receive/security navigation, an unfunded preparation error, and close/reopen/unlock; it did not verify an address, 2FA status or TOTP setup, signing, sending or broadcast. The seed was not read and no screenshots were made in that run. Full GUI TOTP recovery, backup and send workflows remain unverified; that artifact did not wire the backup dialog to the menu. For the earlier `b0291fbd…` artifact, GUI creation followed by offline agent reopen/unlock and SQLite integrity/account-key checks passed. An earlier history crop showed the empty state, but its helper revision was uncertain and it does not prove geometry or safety.
